# Staging Feedback Checklist

스테이징에 올린 변경을 빠르게 검증하고, 개선 요청을 재현 가능한 형태로 남기기 위한 체크리스트다.

- 작성일: 2026-02-15
- 대상 브랜치: `develop` 기반 `feat/*`
- 운영 원칙: 작은 배포 단위 + 고정 테스트 시나리오 + 표준 피드백 포맷

## 1. 사이클 시작 전

- [ ] 이번 배포의 범위를 1~3개 변경으로 제한했다.
- [ ] 테스트 대상 환경(`staging`)과 앱 버전(커밋/PR)을 기록했다.
- [ ] 검증 담당자(웹/모바일)와 검증 시간대를 확정했다.
- [ ] 실패 시 `Ship | Hold | Rollback` 중 어떤 결정을 할지 기준을 합의했다.

## 2. 고정 검증 시나리오

매 사이클 동일하게 아래 3가지 축을 점검한다.

- [ ] 핵심 흐름(정상 경로)
- [ ] 엣지 케이스(빈 값/경계값/권한/네트워크 변동)
- [ ] 회귀 점검(이번 변경과 무관한 기존 핵심 기능)

권장 기록 방식:

| 시나리오 | 결과(PASS/FAIL) | 근거(스크린샷/로그) | 비고 |
|---|---|---|---|
| 핵심 흐름 |  |  |  |
| 엣지 케이스 |  |  |  |
| 회귀 점검 |  |  |  |

## 3. 피드백 전달 템플릿

아래 템플릿으로 이슈를 전달하면 재현/수정 속도가 빨라진다.

```text
[환경] staging / 브라우저(or 디바이스) / 계정
[재현절차] 1) ... 2) ... 3) ...
[기대결과] ...
[실제결과] ...
[로그/에러] ...
[심각도] Blocker | High | Medium | Low
[완료기준] 이 기준 충족 시 종료
```

## 4. 우선순위 처리 규칙

- [ ] `Blocker`, `High`는 현재 사이클에서 즉시 수정/재배포한다.
- [ ] `Medium`, `Low`는 묶어서 다음 사이클 후보로 이관한다.
- [ ] 같은 증상에 대한 중복 보고는 하나의 티켓으로 통합한다.

## 5. 사이클 종료 체크

- [ ] 최종 결정(`Ship | Hold | Rollback`)을 명확히 기록했다.
- [ ] 남은 이슈의 우선순위와 다음 액션을 정리했다.
- [ ] 관련 문서(`docs/WORK_CYCLE.md`, 필요 시 `CLAUDE.md`)를 동기화했다.
